### The repo was deleted and recreated, deliberately

`main` is **one commit** with no history, and that took more than a force-push.

A force-push removes the *reference*; GitHub keeps the objects and serves them
by SHA. Measured, anonymously, with no token, after the first squash:

```
GET /repos/AlgoraLabs-AI/AI-Cloud-Status/commits/132dea3…  →  HTTP 200
"feat(ui,i18n,history): the 24h history stops depending on unrelated categories"
```

So the old history was still publicly readable by anyone holding a SHA. The only
way to actually remove it was to delete the repository and recreate it. After
doing so the same probes return **HTTP 422** — `132dea3`, `7d62aee`, `8cc8ce4`
and `0318842` are all gone.

Two things that squash also cleaned up, both worth knowing about:

- Three commits carried `Co-Authored-By: Claude …`, which put an extra entry in
  the repository's contributor list.
- Those same three were authored with a **personal email address** rather than
  the GitHub `users.noreply` one. A public repo's commit log is plain indexed
  text, and address harvesting from it is routine.

The machine that produced them should set:

```bash
git config --global user.email "<id>+<user>@users.noreply.github.com"
```

That only affects future commits.

Before deleting anything, the squashed commit's **tree hash was compared against
the pre-squash HEAD** and matched exactly (`4c7c0e6…`, 239 files). The squash
provably lost nothing. A local branch `backup-before-squash` still holds the
8-commit development history; it exists nowhere on the remote.

## SmartScreen on Windows is expected, not a defect

Running the published `.exe` raises **"Windows protected your PC … Publisher:
Unknown publisher"**. `Get-AuthenticodeSignature` confirms `Status: NotSigned`.

The binary is authentic — its SHA256 was verified against the published
`SHA256SUMS.txt` and matches (`efc63ce4…`). SmartScreen is not saying the file is
malicious; it is saying it does not know who made it. Two signals feed it, and
this build has neither: a code-signing certificate, and per-binary reputation
built from download volume.

Worth knowing before anyone spends money on it: reputation is keyed to the exact
binary hash, so **every release starts from zero**. An OV certificate (~200-400
USD/yr) removes "Unknown publisher" but not the warning — the certificate itself
accrues reputation over weeks. Only an EV certificate (~300-600 USD/yr, hardware
token, legal-entity verification) bypasses SmartScreen from the first launch.

For a free OSS tool the defensible position is not to pay, and instead to make
verification possible — which `SHA256SUMS.txt` already does.

## The memory soaks: what they proved, and what they did not

Two soaks were run, one per platform. **Both measured the app idle in the system
tray**, and neither exercised the painting path. That distinction is the point of
this section.

### macOS — 62 minutes

| Minute | RSS |
| --- | --- |
| 0 | 203,216 KB |
| 10 | 213,936 KB |
| 20 | 217,056 KB |
| 30 | 217,152 KB |
| 40 | 216,976 KB |
| 50 | 217,056 KB |
| 62 | 218,256 KB |

Rises ~13.5 MB in the first 20 minutes, then flat: minutes 20-62 stay inside a
1.3 MB band and the value **falls** at minute 40. Non-monotonic movement is
noise, not slope. Zero watchdog entries, zero ERROR/WARN, and the window
repainted correctly when restored after 1h03m.

### Windows — 45 minutes, sampled once a minute

Same release binary from Downloads, PID 37516, sampled with a per-sample check
for whether the process owned a **visible** top-level window.

| Minute | RSS | Threads | Handles | Visible window |
| --- | --- | --- | --- | --- |
| 0 | 233,956 KB | 29 | 756 | no |
| 8 | 237,664 KB | 29 | 756 | no |
| 14 | 210,508 KB | 29 | 756 | no |
| 30 | 210,844 KB | 29 | 756 | no |
| 45 | 211,996 KB | 29 | 755 | no |

**RSS went down**, 234 MB → 212 MB, with a step drop at minute 14 (the OS
trimming the working set) and then a 7 MB band with no trend for 31 minutes.
Threads pinned at 29 the whole time and handles at 755-762 — a flat handle count
over 45 minutes rules out the classic Windows handle leak, which nothing else in
this project measures.

At session close the process had been up 3h35m at 218,280 KB.

### The caveat that applies to both

The window was hidden to the tray for the entire Windows run (`ventana_visible`
is 0 in all 46 samples) and from minute 5 of the macOS run.

That matters because the leak these soaks were chasing is the **renderer/texture
cache** one described in `rowwidget.go` — the one the per-row widget cache was
built to fix, which grew the process "by gigabytes over a long run" by pushing
"hundreds of canvas objects (labels, hyperlinks, raster textures) per second"
through that cache. **That cache is filled by painting.**

`refreshLocked` has no visibility guard — it keeps calling `buildRows()` with the
window hidden — so the widget-tree half of the work *was* exercised. The painting
half was not. How much Fyne skips for a hidden window was not verified here, so
the honest statement is the narrow one:

> No leak in the poll / update / log / capture path with the app idle in the
> tray, over an hour on macOS and 45 minutes on Windows, with thread and handle
> counts flat.

Not "no leak".

**The measurement still owed** is a soak with the window visible and in the
foreground. The instrumentation for it already exists and records visibility per
sample, so the same run can capture both phases and the slopes compared directly
on one process:

- `scripts`-less helper used here: sample RSS + `IsWindowVisible` once a minute,
  hidden for ~15 min, then visible for ~25.
- If the painting path leaks, the slope changes at the transition. If it does
  not, the question is closed with far better evidence than a hidden soak.

## Log rotation is unobservable by design

Measured on macOS: `acs.log` grows **924 B/min**. Against the 8 MiB ceiling that
is **6.2 days** to a first rotation.

This upgrades the open item from "we ran out of time" to "no verification
session can ever sit through it". Rotation is covered by unit tests only —
including the platform-sensitive part, renaming a file that is open for append —
and `platform-coverage.md` should say so rather than listing it as pending work.

## Still open

1. **Linux GUI.** Never compiled or run by anyone. The README says so in the
   download table, and `platform-coverage.md` tracks it.
2. **Visible-window soak.** See above. This is the real remaining memory
   question; the two soaks did not answer it.
3. **Tray menu does not re-translate on language change.** Found during the
   macOS pass, NOT macOS-specific, no build tags — it reproduces on Windows.
   `updateTray()` rewrites only `Items[0]`; the rest is built once in
   `setupTray()`, which is not called again when the language changes. The fix
   is to re-run `setupTray`, but that re-registers the icon and `SetOnTapped`,
   so it wants someone who can exercise the Windows tray. Deliberately not
   touched at release time.
4. **Fyne's own dialog buttons follow the OS locale, not the app's.** A
   Spanish-locale machine shows "No / Sí" on a confirm dialog in an app set to
   English. Same family as the injected-"Quit" issue.
5. **Intel Macs.** Apple Silicon only so far.

## Next release mechanics

`release.yml` fires on a `v*` tag. Nothing else triggers it, and a plain commit
to `main` costs zero Actions minutes.

One annotation appeared on this run and is not ours: `actions/checkout@v4`,
`actions/setup-go@v5` and `actions/upload-artifact@v4` still declare Node 20 and
the runner forces them onto Node 24. Harmless today; they will need bumping.

If a README-only follow-up ships (e.g. a "first launch on Windows" section
mirroring the macOS one), it lands as a normal commit and waits for `v1.0.1` —
the published `v1.0.0` tag is immutable.
